# rekordbox vs RBX: Link behavior and side effects

The question this report answers is: **when something connects, disconnects, or sends a request, what does each application do, and what changes as a result?**

This compares the inspected macOS rekordbox 7.2.11.0342 implementation with RBX at `29dc37841ed1ef4eca4ab07d6308adbc25444bdb` and the working-tree source inspected on 2026-10-04.

“Same” is limited to the behavior stated in that row, not complete protocol compatibility. “Different” identifies a demonstrated code or reply difference. “Not established” means there is insufficient evidence to compare the outcome.

**Notes describe the direct side effect established by the code. Player-screen symptoms, playback failures, and performance effects are marked unknown unless tested.** No new hardware test was performed. Evidence IDs link to the inspected artifacts in the appendix.

## Connecting and disconnecting

| Event / feature | What rekordbox does | What RBX does | Same / different | Notes: side effect and evidence |
|---|---|---|---|---|
| A service fails during startup | Retries startup up to three times, with one-second waits. | Returns the startup error without that retry loop. | Different | RBX does not automatically retry that failed startup within the same call. Whether a specific failure clears during rekordbox's retries is untested. V3 `InnerLinkAPI::start`; R1 `Link::start`. |
| Starting Link before a device number is assigned | Starts NFS/system manager; initializes the database daemon through the link-connected callback. | Binds beacon, database, and file services during startup. | Different | RBX database sessions can open before number acquisition and use fallback device number 17 when the current number is zero. Whether a player attempts this is unknown. V3 `notifyLinkConnect`; R1 start; R3 session open/networking. L1 also records service startup before LINKUP. |
| Which network interfaces receive requests | Inspected UDP/NFS sockets bind to all local addresses. | Service sockets bind to the selected interface IPv4 address. | Different | RBX's service sockets do not bind the other local IPv4 addresses. Effects on multi-interface player connections were not tested. V1 UDP startup; V7 socket startup; R1 `service_bind_address`; R2 startup. |
| Choosing a device number | Has wired 17/18, wireless 41–44, and Mode23 branches; inspected probe timer is 200 ms. | Uses 100 ms steps, three discovery packets, and candidate rounds across 17, 18, 41–44 without those mode-selection branches. | Different | Probe timing and candidate selection differ. Faster connection or a collision rate cannot be concluded from these constants. V1 system-manager state branches; R2 `Join`. |
| Another device announces an occupied number while RBX is probing | Records occupied candidates from keepalives during vendor probing state 5. | Does not record probing occupancy through `Join::hear_keep_alive`; uses its reply path. | Different | That keepalive alone does not eliminate the candidate in RBX's probing state. A resulting collision is not demonstrated. V1 `readConfigNotify`; R2 join. |
| A device asks which numbers are occupied | Reads subtype-2 number bitmasks and echoes the request counter in its reply. | Treats subtype 2 as ordinary number/round fields and compares a requested number. | Different | RBX's decision to answer is based on a different field interpretation, not the vendor bitmask. Exact player reaction is unknown. V1/V6 `readIdBlkRequset`; R2 `NumberProbe`/`hear_probe`. |
| Original CDJ-2000/CDJ-900 announces itself | Applies the minor-0 model exclusion only in the wireless branch. | Applies that exclusion without a wired/wireless condition. | Different | A wired announcement excluded by RBX does not bring its Link state up through this eligibility check; the vendor wireless-only restriction does not exclude it on the same basis. Full connection testing is absent. V1 `linkUpFunc`/`readFrame`; R2 `brings_link_up`. |
| Another device claims our number after joining | Sends disconnect, clears membership, and retries number acquisition. | Has no equivalent running-state keepalive collision transition. | Different | RBX does not resolve that collision through the vendor's reset/retry path. Subsequent device behavior is unknown. V1 `readConfigNotify`; R2 join. |
| An already-known device sends discovery again (`00`) | Removes matching stored MAC membership. | Ignores this packet type. | Different | RBX retains membership in response to this packet; rekordbox removes the matching record. Reconnect symptoms are untested. V1 `readDiscovery`; R2 `hear_announce`. |
| A matching time-server request arrives (`04`) | In the inspected running states, clears members and returns to number acquisition. | Does not handle this request. | Different | RBX does not perform that request-driven reset/rejoin. V2 `readTimeServerRequest`; R2 announcement dispatch. |
| A rejection arrives (`09`) | Sends `08`, records rejection, and drops members. | Ignores this packet type. | Different | RBX does not acknowledge rejection or clear members through this branch. Device response is unknown. V2 `readReject`; R2 announcement dispatch. |
| One logical deck disconnects (`07`/`08`) | Removes by the device number carried in the packet, with paired-ID handling for 9/11. | Removes player/greeting entries by sender IP; does not remove the separate peer entry here. | Different | RBX removes all player entries sharing that IP, not just the packet's numbered member, and retains the peer entry until another path removes it. This is a demonstrated state effect, not a tested screen symptom. V2 `readDisconnect`; R2 `remove_players_at`/announcement dispatch. |
| Compatibility reset arrives (`0b`) | Resets only with a nonzero system-manager state. | Resets without that guard. | Different | RBX also resets in a state where the vendor guard would skip it. Effect during a real startup race is unknown. V2 `readCompatibiltyMode`; R2 announcement dispatch. |
| A known number announces a changed IP | Compares IP/MAC and replaces changed membership. | Updates name/time on an existing player entry, but not its stored address; updates the separate peer address. | Different | Player and peer records can hold different addresses after that keepalive. Delivery of subsequent commands in a real address-change scenario is untested. V1 `readConfigNotify`; R2 keepalive updates. |
| A multi-deck device announces one identity | Creates paired logical members for IDs 9/11, with additional OPUS-QUAD entries in the inspected branch. | Creates entries from received keepalive/status IDs, without equivalent synthesis. | Different | RBX does not create those additional members from the one announcement. It can still learn IDs that arrive separately. Whether a particular device sends them is not established here. V1 `readConfigNotify`; R2 receive handlers. |
| A player stops sending traffic | Uses 10-second member ageing; inspected wireless path multiplies it by 18. | Uses a six-second player timeout, refreshed by status and keepalive. | Different | The removal thresholds and refresh sources differ. This does not prove earlier removal in every traffic pattern. V1 ageing/`readConfigNotify`; V2 constructor; R2 timeout paths. |
| All peer keepalives stop | Uses ageing timers for membership. | Peer expiration is checked while processing received keepalives, not by a periodic peer-expiry timer. | Different | Without subsequent keepalive processing, that expiry path does not clean RBX's peer map. V1/V2 ageing; R2 `hear_announce`. |
| Network disconnects or wireless network changes | Checks IP change, network disconnect, and wireless BSSID. | Checks whether interface name/address remains present; app reporter drops the session on reported down state. | Different | A BSSID change alone is not detected by an equivalent RBX BSSID check. Actual cable/wireless recovery is untested. V2 `timerCallback`; R2 monitor; R1 app reporter. |
| User stops Link | Stops common timer/beat, then NFS, then system manager. | Stops beacon, then database, then files. | Different | Shutdown order differs; a player-visible failure caused by the order is not established. Exact vendor goodbye packets and accepted-client shutdown parity remain unknown. V4 `InnerLinkAPI::stop`; R1 stop; R3 networking. |
| Player disconnects but file service stays running | Has mounted-host structures and explicit unmount cleanup. | Beacon disconnect/reset does not clear file-service mounted-host state. | Not established for full parity | RBX retains mounted-host state across a beacon-only disconnect/reset. Vendor cleanup on every disconnect path has not been traced. V7 mount helpers; R1/R2/R5 service ownership. |

## What remains unknown

No claim is made here that a code difference necessarily breaks ordinary Link Export. The following side effects still require runtime/device evidence:

- Exact player-screen responses to different status/error values and missing request handlers.
- Loading/seeking effects of missing track-specific VBR information.
- Full reconnect behavior under cable loss, wireless changes, address changes, and number conflicts.
- Vendor callbacks behind settings, mobile, monitoring, and library-sync messages.
- Every menu, cue, waveform, artwork, and analysis payload; sort/collation parity.
- Vendor goodbye packets, accepted-client shutdown, full export-path selection, mount accounting, malformed-RPC behavior, and directory-cookie corner cases.

These are evidence gaps, not assumed failures. In particular, a vendor callback call proves delegation, not every downstream operation.
